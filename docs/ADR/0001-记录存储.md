# ADR-0001：记录用 Markdown 正本 + SQLite 索引

- 状态：已采纳
- 日期：2026-10-16

## 背景

记录要同时满足两个需求，而它们在存储上是矛盾的：

- 十年后还能打开、能读、能导出、能进 Git；
- 按维度、日期、指标、关键词快速查。

一个存储做不到两头。选纯数据库，数据变成黑盒，用户不敢用。选纯文件，检索靠遍历，几千条以后就慢。

## 决定

**两处都写，Markdown 是正本，SQLite 是索引。**

- 每条记录一个 Markdown 文件：`records/<年>/<月>/<日期>-<类型>-<短 id>.md`，YAML frontmatter 存元信息，正文分段存原始材料。
- SQLite（`pkbrain.db`）存元信息表、指标表与 FTS5 全文索引，可随时由 Markdown 重建。
- 两者不一致时，以 Markdown 为准。

## 后果

好处：

- 数据是可读的纯文本，Git 能管版本，用户能随时走人。
- 检索、统计、后续的向量化都走数据库，快。
- 索引坏了删掉重建即可，没有数据损失。

代价：

- 写入要落两处。同一 id 重复写入按覆盖处理，测试里覆盖了这个路径。
- 目前没有「从 Markdown 重建索引」的命令。M1 要补 `pkbrain reindex`，否则「可重建」只是说法。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 只存 Markdown | 全文检索要自己实现，指标统计要遍历全部文件 |
| 只存 SQLite | 数据变成黑盒，违背本地优先与可迁移 |
| SQLite 作为正本 + 定期导出 Markdown | 导出是异步的，崩溃窗口内会丢数据 |
| Obsidian 库 + 插件 | 绑定到别人的数据模型，PKBS 的维度落不下去 |
