# ADR-0002：M0 先用一版最小 PKBS 子集

- 状态：已采纳（临时）
- 日期：2026-10-16

## 背景

PKBrain 是《个人知识库标准与规范（PKBS-1.0）》的实现，但 PKBS 正文尚未并入本仓库。

产品文档里到处是 `R1–R7`、`D0–D7`、`P0–P4` 这些编码，而 `schema/` 需要的是能落地的字段定义。没有定义，M0 第一步就卡住。

## 决定

先写一版**最小子集**，明确标注为临时，落在三个文件里：

- `schema/pkbs.yaml`：记录类型、维度、隐私分级、采集通道、confidence 规则、路径。
- `schema/metrics.csv`：指标字典 + 抽取正则。唯一事实来源，抽取器与渲染器都读它。
- `schema/record.json`：由 `pkbrain.models.Record` 生成，测试核对不漂移。

范围：2 种记录类型（R1 每日快照、R2 即时记录）、4 个维度（D1 身体、D2 情绪、D3 事业、D4 关系）、3 级隐私（P0/P1/P2）。其余编码留空。

PKBS-1.0 正文到手后，用一份后续 ADR 整体替换 `schema/`，并写迁移脚本。

## 后果

好处：

- M0 当天就能开工，不被外部文档阻塞。
- 维度与指标的耦合实测过了：正则抽取、range 校验、指标表渲染都走通了同一份字典，后面替换标准是改数据，不是改代码。

代价：

- **字段名是猜的**。`dim`、`confidence`、`privacy` 这些名字按 PKBS 的命名习惯定的，可能与正式版不一致。
- 已经产生的记录带着 `version: 0.1.0-min`，替换 schema 后需要迁移。
- 只有 4 个维度，产品文档说的「全维度」在 M0 是不成立的。这是范围取舍，不是遗漏。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 等 PKBS 正文 | 阻塞全部开发，且正文什么时候到不可控 |
| 直接照搬某个现成的人生维度模型 | 名字对不上 PKBS，后面迁移更麻烦 |
| 不定义 schema，字段随抽取自由生长 | 用户要的正是「结构化」，自由生长会让报表全乱 |
